# Developer Backlog

Running list of feature requests, UX polish, and known issues to address in
future batches. **This file is dynamic** — add new items as they come up,
mark items done (or remove) when they ship in a batch.

## How to use this file

- **Add new entries** to the bottom of the relevant section. Keep each
  entry to a short title plus a one-paragraph description (what + why).
- **Tag** with priority (`Low` / `Medium` / `High`) and category in the
  table column.
- **Cross-link** to source when applicable: a test-log entry, a chat
  conversation, an issue number.
- **When picked up**: move the entry into a batch implementation plan
  (`docs/developer/batchN-implementation-plan.md`) and either delete it
  here or strike it through with a pointer to the batch. Keep the file
  short — this is a backlog, not an archive.

For comparison: `developer-notes.md` records *design decisions already
made* (with a "what to do next when ready" section). This file records
*work not yet started*.

| 4 | Medium | **Auto-assign evaluators: confirm-and-review step before emails go out.** Today the ReDIB coordinator clicks the per-call auto-assign button and the system immediately creates `Evaluation` rows AND sends assignment emails. The assignments can be edited after, but the emails are already out — hard to walk back. Add a two-step flow: (1) auto-assign computes a *preview* (which evaluators would be assigned to which apps, with COI/area annotations); (2) coordinator reviews and tweaks; (3) coordinator clicks "Confirm and notify" which persists the assignments and triggers the emails. Affected: `evaluations/views.py:auto_assign_call`, `evaluations/tasks.py:assign_evaluators_to_call`, plus a new preview template. **Note (2026-04-17):** The confirm step should also unify the auto-assign / manual-assign / combo workflows. A coordinator may auto-assign most evaluators and then manually add or swap a few — or skip auto-assign entirely and hand-pick all evaluators. The confirm-and-review screen should work for all three paths: show the proposed roster (however it was built), let the coordinator finalize, and only then persist assignments + fire emails. A bug where manual assignment didn't transition `pending_evaluation` → `under_evaluation` was fixed in commit `07468fc`; the confirm step should make this kind of state-sync issue structurally impossible. (Source: 2026-04-16 chat + 2026-04-17 livetest.) |

| 12 | Medium | **Dedicated `edits_requested` application status.** When a feasibility reviewer requests edits, the application is currently shoved back into `status='draft'` and `submitted_at` is cleared (`applications/views.py:761-768`), reusing the never-submitted draft state. | 16 | Medium | **Distinguish "accepted by node, awaiting applicant" from "accepted by applicant".** There are effectively two acceptance steps — the node coordinator accepts an application (`status='accepted'`), then the applicant must accept within their 10-day window (`accepted_by_applicant=True`) — but both currently surface identically as "accepted" in every status badge and coordinator view. There is no way, from the status or any coordinator-facing list, to see that an applicant still hasn't accepted (e.g. REDIB-2601-023 and -027 sat node-accepted but applicant-unaccepted while -005/-011/-016/-025 were fully accepted, all indistinguishable). Surface the distinction without adding a full workflow phase: the data already exists on `Application` (`accepted_by_applicant`, `accepted_at`, `acceptance_deadline`, `handoff_email_sent_at`). Options to evaluate — a derived sub-state badge ("Accepted — awaiting applicant" vs "Accepted — confirmed") computed from those fields, or a lightweight `applicant_accepted` flag column in the relevant lists, with the acceptance deadline shown for the pending ones. Affected: `templates/includes/status_badge.html` and any per-role rendering, the coordinator/Access Tracking views and call-detail status wall (`calls/views.py`, `applications/views.py`), and possibly a filter so coordinators can pull "node-accepted but not yet applicant-confirmed". (Source: 2026-06-22 chat.) |
| 15 | High (before next call) | **Gate evaluated applications behind a ReDIB-coordinator release, then batch node resolution.** Today, once an application's assigned evaluations are all submitted it independently transitions `under_evaluation` → `evaluated` and immediately becomes actionable: it is pushed to the node coordinator, who can accept it, which bounces it to the applicant, who accepts, which makes it active — all asynchronously, one application at a time as each finishes evaluating. This biases node decisions: a node coordinator resolves applications piecemeal instead of weighing the whole pool of approved applications against limited capacity. Applications should instead be considered **all at once, after every evaluation score for the call is in**, so the node can unbiasedly sort the full set into accepted / waitlisted / rejected. (Note for the record: it is the **node coordinator** who technically makes the call on how each applicant is treated for assignment based on the evaluations — not the ReDIB coordinator and not an automatic rule.) Desired system: keep evaluated applications in a held/pending state until the ReDIB coordinator explicitly **releases** them back to the nodes for assignment — i.e. a per-call gate (all evaluations complete → ReDIB coordinator reviews/releases → node coordinators do batch resolution). Affected areas to design around: the `evaluated` → `accepted`/`pending`/`rejected` transition and the resolution services (`applications/services/node_resolution.py`, `applications/services/resolution.py`), the node-coordinator resolution views/forms, and likely a new release action + state (or a per-call "released for assignment" flag) plus the Access Tracking / call-detail UI. **Letting it slide for the current call (REDIB-2601)** since resolution is already happening; required before the next call. (Source: 2026-06-08 chat.) |

## Tooling / data ingestion

| # | Priority | Item |
|---|----------|------|
| 14 | Medium | **User guide: collapse the markdown↔PDF disconnect.** Today there are two parallel artifacts: `docs/USER_GUIDE.md` (the source-of-truth markdown, edited by developers) and `static/documents/user_guide.pdf` (the served version, linked from `templates/base.html:43` via `{% static %}`). The PDF is hand-rebuilt from the markdown and committed as a binary, which means (a) the two drift silently — same mtime on 2026-04-20 today, but no enforcement — and (b) under `ManifestStaticFilesStorage` the served URL gets a content hash that changes every rebuild, breaking any external link to the PDF (e.g. links shared by email). Options to evaluate: (1) render the markdown to HTML on the fly and serve it as `/help/user-guide/` (or per-section URLs), so external links remain stable and updates flow automatically from a single source; (2) keep PDF but auto-build from the markdown in CI on every merge to main, fail the build if they diverge; (3) some combination — HTML primary, PDF generated for download. Should also revisit cross-linking from in-app pages (e.g. an "?" icon on the evaluator dashboard linking to the relevant section). (Source: 2026-05-20 chat — coordinator emailing first-time evaluators with the portal URL.) |
| 13 | Medium | **`populate_redib_users` sync semantics.** The current loader (`core/management/commands/populate_redib_users.py`) is unsafe to re-run on prod for two reasons. (1) It unconditionally `user.set_password('changeme123')` on every row (lines 189-190), so any user who has set their own password loses it. (2) It uses `update_or_create` with TSV values winning unconditionally — so any field that drifted from the TSV after first load (e.g., a coordinator edited their phone in `/profile/`, or we toggled `is_active` directly via the shell to handle an ops issue like activating Benito on 2026-05-20) silently gets stomped on the next reload. Decide a conflict-resolution policy: who wins (TSV / DB / per-field), do we need a `--dry-run` mode that diffs and exits, do we only set the password for newly-created users, and should `update_or_create` switch to "only update fields that changed in the TSV" (read the prior TSV from a checked-in snapshot, diff, apply only the deltas). Until this is sorted, do targeted DB updates by hand for one-off ops changes. (Source: 2026-05-20 chat — activating bjrubio@ucm.es from the new TSV without running the loader.) |
| 6 | Medium | **xlsx → tsv conversion + QC tooling.** The reference TSVs in `data/` are produced by exporting from Microsoft Excel on Windows, which writes Windows-1252 (CP1252) text and CRLF line endings. Our loaders assume UTF-8, so non-ASCII names (e.g. `Asociación`, `Compostela`) crash the import on the first row. Today the workaround is a manual `iconv -f cp1252 -t utf-8` pass plus eyeballing column counts. Build a small `manage.py` command (or standalone script) that takes the source `.xlsx`, writes UTF-8 TSV, and runs file-specific QC. Specific checks observed in real data so far that need automated catching: encoding (force UTF-8 output); trailing-tab artifacts in headers; leading/trailing whitespace in cells; underscore-style phone-extension suffixes (e.g. `+34 91 ... _5404`); typos in enum-valued columns (e.g. `prelcincal` for `preclinical`, `Public Research Organisation (PRO)` exact-spelling check); separator drift (`,` used where `;` is required, e.g. `users.tsv` `areas`); ambiguous booleans (blank vs explicit TRUE/FALSE — confirm intent); FK lookups (`organization_name` → `organizations.tsv:name`; `roles` `node_coordinator:CODE` → `nodes.tsv:code`; `equipment.tsv` `node_code` → `nodes.tsv:code`); duplicate natural keys; required columns present. Should be runnable per-file (`--file organizations`) and as a batch. (Source: 2026-04-16 chat / real-data prep.) ; we need to deal with phone number extentions in the xls file (also xls thows an error for + becuase it thinks it is a formula, not sure how some field have it and others do not)|
