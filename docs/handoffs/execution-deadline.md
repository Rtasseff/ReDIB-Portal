## Goal

Backlog **#80(a)**, decided by Ryan 2026-09-11. Today a call has one
`execution_end` and every accepted project inherits it. In practice the date
is wrong for many projects — REDIB-2601's fifteen still-running grants are
being held to 2026-10-30, a date nobody believes, which is why the completion
reminders had to be paused in prod (#80). The node coordinators are the
people who know when a project's access will actually end, and they already
have a moment where they commit to the project: **when they set the approved
hours** — at node resolution, and at *Promote to Accepted*.

This branch gives each application its own execution end, **set by the node
at that moment, defaulting to the call's date**, editable later by the node,
and read by the two reminder tasks. It is deliberately small: one nullable
field, one method, one input in three places, five one-line reader changes.
No per-equipment dates, no approval step, no history screen.

The reminders stay paused in prod until this is deployed and REDIB-2601's date
is corrected; re-enabling is a prod action and is **not** part of this branch.

## Decisions (already made — build to these)

**D1 — The field.** `applications/models.py`, next to `accepted_at` /
`acceptance_deadline` / `handoff_email_sent_at` (~`:247–262`):

```python
execution_end = models.DateTimeField(
    null=True, blank=True,
    help_text="Node-set end of this project's execution period. "
              "Empty means the call's execution_end applies.",
)

@property
def effective_execution_end(self):
    return self.execution_end or self.call.execution_end
```

Null means *inherit the call's date*. That is what keeps the call-level date
a working lever: editing a call's `execution_end` on the call form still moves
every project that has no override — including all fifteen REDIB-2601 ones,
which get **no backfill**.

**D2 — One write rule.** A model method, no save (callers save):

```python
def set_execution_end(self, date_value):
    """date_value: a date. Stores 23:59:59 local on that day, or None when it
    equals the call's own date (so the call-level date stays the default)."""
```
- Normalise to end-of-day **local** exactly as `calls/forms.py` does for the
  call's own end fields (`:64–75`, `time(23, 59, 59)` in
  `timezone.get_current_timezone()`).
- If the resulting date equals `self.call.execution_end` (compare local
  dates) → `self.execution_end = None`. Otherwise store it.
- Validation is the caller's, and it is one rule: the date must not be before
  `call.execution_start` (local date). Bad or missing input → error message,
  re-render, **nothing saved** — the hours submitted alongside are not saved
  either; the coordinator re-submits the form.

**D3 — Where it is set.** The same `<input type="date" name="execution_end">`
in three places, labelled *Execution period ends*, prefilled with
`application.effective_execution_end|date:"Y-m-d"`, help text: *Defaults to
the call's date. Change it if this project's access will run to a different
date.*

- (a) **Node resolution review** — `templates/applications/node_resolution/review.html`,
  under the approved-hours table (`~:233–267`), above Comments (`~:289`).
  View `node_resolution_review` (`applications/views.py` ~`:2490–2575`) reads
  it beside the `hours_approved_<id>` fields and applies it **only when
  `resolution == 'accept'`** — a waitlisted application gets its date at
  promotion, a rejected one has none. Pass it through
  `NodeResolutionService.apply_node_resolution` (`applications/services/node_resolution.py:150`)
  as a new optional argument, or apply it in the view after the service
  returns — whichever keeps the service's existing save order intact; check
  where the application is saved today (`aggregate_application_resolution`)
  and save `execution_end` in the same place or with
  `update_fields=['execution_end']`.
- (b) **Promote to Accepted** — `templates/applications/promote_waitlist_confirm.html`
  under the hours table (`~:32–63`); view `promote_waitlisted_application`
  (`applications/views.py:1543`) applies it right after the hours loop
  (`~:1629`), before `application.save()`. Keep it a **separate block** —
  `rehearsal-guards` G2 is adding its own block after that `save()` (the
  `NodeResolution` update), and you will rebase over it.
- (c) **Later edits** — on the **application detail page**
  (`templates/applications/detail.html`), in the access section (`~:218`,
  where `hours_requested / hours_approved` are listed): for users where
  `can_manage_application` is true (the context var already exists, `:61`)
  and the application is `accepted` and not `is_completed`, show the effective
  date with a small **(set by node)** marker when `application.execution_end`
  is set, plus the same input and an *Update* button posting to a new
  POST-only view `applications:set_execution_end` (`@login_required`,
  `_can_manage_application` from `applications/views.py:1514`, D2, one
  `messages.success`, redirect to detail). Everyone else, the applicant
  included, sees the effective date read-only on the same line.
- **Access Tracking** (`templates/access/access_tracking.html`, rows at
  `:48`): show `ends <effective date>` as small text in the status cell for
  accepted, not-completed rows. Read-only; the edit is on the detail page.

**D4 — Who reads it.** `applications/tasks.py`, five sites, each
`app.call.execution_end` → `app.effective_execution_end`: `send_waitlist_digest`
`:553`, `:572`; `send_completion_reminders` `:682`, `:708`, `:742`. Nothing
else reads the date (checked at cut: no email template, no other view).

**D5 — Multi-node.** Any node coordinator with equipment on the application
(that is what `_can_manage_application` already grants) may set or change it;
last edit wins. Settled; do not build anything to reconcile.

**D6 — Not a call-form change.** `Call.execution_end` and its form are
untouched; it remains the default and the interim lever for REDIB-2601.

## Tests — `tests/test_execution_deadline.py`

1. `effective_execution_end` is the call's when the field is null, the
   override when set.
2. `set_execution_end`: a different date → stored at 23:59:59 local; the
   call's own date → stays `None`; across the late-October DST change the
   stored local time is still 23:59:59.
3. Node resolution **accept** with a date → override stored; with the call's
   date → null; with a date before `execution_start` → error and neither date
   nor hours saved; **waitlist** with a date → ignored (still null).
   Fixtures: `tests/test_release_gate.py` / `tests/test_design.py` drive
   `node_resolution_review`.
4. Promotion with a date → stored. Fixture:
   `tests/test_backfill_waitlist_hours_approved.py`.
5. `set_execution_end` view: a node coordinator of the application's node can;
   a node coordinator of another node and the applicant cannot (whatever
   `_can_manage_application` yields today — match it, don't redesign it).
6. `send_completion_reminders`: an application whose override is 40 days
   after the call's date gets **no** milestone nudge in the call's window and
   **does** get one in its own. Fixture:
   `tests/test_closeout_completion_reminders.py`. One equivalent test for
   `send_waitlist_digest`.
